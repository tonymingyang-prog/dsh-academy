LESSON 08 实战

自动化、定时任务与上线

让 DSH 按计划自动干活，并把它安全地放到反向代理后面。学完你能配置定时任务、排查公开部署的 403 和 WebSocket 问题。

40 分钟 6 个步骤 实战

学完你能

  • 创建带 IANA 时区的定时任务并理解投递与补投规则
  • 按反向代理要求配置 --public-url 与 --trusted-host
  • 完成一次公开部署的上线验收与回滚检查
STEP 01

创建定时任务

在对话里让模型创建提醒，或从侧栏的自动化任务页面新建。规则要写清频率与时区，例如“每天 Asia/Shanghai 09:00 汇总昨天的 CI 失败”。

text
每天 Asia/Shanghai 09:00 汇总昨天的 CI 失败，并给出修复建议
支持一次性延迟、绝对时间、固定间隔、带 IANA 时区的每日/每周规则和五字段 cron；子代理看不到这些工具。
STEP 02

理解投递与补投

宿主运行期间，到期的提醒会恢复原会话并排入 follow-up，不打断当前工作。重启后只补投逾期的一次性任务，或每条重复任务最近错过的一次；宿主关闭期间调度停止。

保存的发送记录只证明消息已进入对话收件箱，不代表模型完成了所请求的工作。
STEP 03

准备反向代理

代理必须保留浏览器可见的 Host、剥离挂载前缀、转发 Upgrade 与 Connection 头，并把 cookie 的 Path 改写到挂载路径。对 /ui 的请求必须以 /ui/ 抵达，否则拿不到会话 cookie。

text
浏览器 → https://app.example/ui/ → 代理剥离 /ui → 监听器 /api/...
STEP 04

启动公开部署

用 --public-url 公告浏览器实际访问的地址，用 --trusted-host 点名浏览器使用的 authority。前者只影响打印与运行时上下文，不授予信任；后者才决定 API 是否被放行。

sh
dsh --profile web --public-url https://app.example/ui/ --trusted-host app.example
STEP 05

处理 TLS 与 cookie

可以在代理处或监听器上终止 TLS。监听器自己终止时传 --tls-cert 与 --tls-key，文件相对进程工作目录解析，缺失或无效会启动失败而不是回退 HTTP。

sh
dsh --profile web --tls-cert ./cert.pem --tls-key ./key.pem --public-url https://app.example/ --trusted-host app.example
TLS 监听器会给会话 cookie 加 Secure；浏览器侧链路应保持 HTTPS，否则 cookie 不会回传。
STEP 06

上线验收与限制暴露面

从外网打开 /ui/，确认页面、API 与 WebSocket 都正常；检查 403、登录跳转和 cookie 作用域。把监听端口限制在可信代理或内网，打印的 URL 带启动 token，只发给预期用户。

sh
curl.exe -I https://app.example/ui/
PITFALLS

常见坑

只配了 --public-url 或代理改写了 Host，所有 API 返回 403--public-url 只是公告；浏览器使用的 authority 必须用 --trusted-host 点名，同时让代理原样转发浏览器可见的 Host。
页面能开，但流式输出和状态不更新代理没有转发 WebSocket 升级；确保 Upgrade 与 Connection 头到达监听器。
宿主重启后定时任务没有按预期补跑重复任务只补最近错过的一次，一次性任务才补逾期；需要严格一次性的调度请放到外部调度器。
把带 token 的启动 URL 发到了公开渠道该 URL 携带进程凭据，只能发给预期用户；泄露后重启进程更换 token，并检查访问日志。

验收清单

  • 定时任务的频率与时区在自动化任务页面显示正确
  • 知道宿主关闭期间不会投递，重启只补最近一次
  • 外网访问 /ui/ 返回 200，API 没有 403
  • WebSocket 正常，HTTPS 下 cookie 带 Secure 且 Path 指向挂载前缀
  • 监听端口只对可信代理或内网开放，带 token 的 URL 没有外泄
