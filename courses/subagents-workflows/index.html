子智能体与工作流

用子智能体隔离上下文，用工作流脚本把几十个独立任务并行跑完。学完你能判断什么时候该委派、什么时候该自己干。

35 分钟 5 个步骤 实战

学完你能

  • 区分 spawn 与 fork，按上下文需求选择委派方式
  • 用 list_agents、send_message、interrupt_agent 管理子代理
  • 写一个带阶段和并行分支的工作流脚本并汇总结构化结果
STEP 01

先判断该不该委派

子代理适合边界清楚、可独立验收、上下文可隔离的任务，例如逐包审计、并行调研。需要频繁来回确认或共享大量隐式上下文的任务，自己做完更快。

委派不是免费扩容：每个子代理都要重新建立上下文，任务描述必须自包含。
STEP 02

选择 spawn 还是 fork

spawn 创建全新子代理，不继承父会话历史；fork 用父会话已完成的轮次作为种子，适合接着当前讨论往下做。两者都受委派深度限制，子代理也能再委派。

text
subagent      → 全新上下文，任务自包含
subagent_fork → 继承父会话已完成轮次
STEP 03

管理和继续子代理

list_agents 列出直接子级及其 running/inactive 状态；send_message 给运行中的子代理补充指令，或唤醒可继续的子代理；interrupt_agent 只停止当前工作，之后仍可继续对话。

text
list_agents()
send_message(agent_id, '补充要求：只读，不改文件')
interrupt_agent(agent_id)
外部执行（如 ACP 后端）完成后不可继续对话；只有本地可继续子代理支持 send_message。
STEP 04

写工作流脚本

工作流是一段模型编写的 JS 脚本，用 agent() 启动子代理，用 parallel() 或 pipeline() 组织并发，用 phase() 和 log() 汇报进度，最后 return 一个 JSON 值。

js
const pkgs = args.packages
phase('audit')
const reports = await parallel(
  pkgs.map((p) => () =>
    agent(`审计 ${p} 的依赖与许可证风险，只读`, { label: p, phase: 'audit' })
  )
)
return reports.filter(Boolean)
STEP 05

控制规模并汇总

给脚本传 meta（name、description、phases）和 args，用 maxTotalAgents 限制子代理总数。结果要自己过滤 null、去重、按证据排序，不要把原始输出直接交给用户。

text
workflow({ script, meta: { name: 'pkg-audit', description: '逐包审计依赖风险' }, args: { packages } })
钩子参数写错会抛 fatal 错误并终止整个脚本，而不是默默变成 null；先小规模试跑。
PITFALLS

常见坑

子代理反复问同样的问题任务描述缺少自包含上下文；把路径、验收标准、禁止事项一次写全，或改用 fork 继承父会话。
子代理看不到 schedule 等工具委派行默认 deny 了这些工具，子代理无法创建定时提醒；定时任务应由父会话或人创建。
多个子代理并行改同一批文件，产生冲突只让子代理读和产出建议，写操作由父代理串行执行；或按目录切分互不重叠的写范围。
工作流脚本报 fatal，整次运行失败检查 agent() 的选项名、schema 是否在支持子集内、是否超过并发上限；fatal 是设计上的响亮失败。

验收清单

  • 能说出一个适合委派和一个不适合委派的任务
  • 成功用 spawn 或 fork 启动过子代理并拿到结果
  • 用 list_agents 看过子代理状态
  • 跑通过一个带 phase 与 parallel 的工作流
  • 对工作流结果做过过滤与去重再汇报
